## 2026-09-15 — Leader — Direct fix: client hardcoded `localhost:4000`, unreachable from the customer's real browser

- Task IDs touched: None (critical customer-reported bug, found and fixed live)
- What changed: Customer reported registration/login failing with "Something went wrong" in their actual browser. Every server-side check from inside this session (curl, direct Prisma queries, and even an automated Playwright browser driven from this same session) succeeded without any issue — the bug was NOT reproducible from inside the sandbox. Added temporary diagnostic logging (server-side request logging in `index.ts`, client-side raw-error logging in `apiClient.ts`) and had the customer retry with browser DevTools open: the real error was `TypeError: Failed to fetch` with **no accompanying CORS message at all** — meaning the browser never reached `http://localhost:4000` in the first place (a genuine CORS rejection always logs its own separate message; a bare connection failure does not). Root cause: this session's execution environment forwards only the client dev-server's port to the customer's actual browser — `API_BASE_URL`'s hardcoded default of `http://localhost:4000` (set all the way back in T-006) pointed at port 4000 on a machine the browser has no route to, since that port was never part of what gets forwarded. The page itself (port 5173) loaded fine because that port IS forwarded, which is what made this so confusing — "the site loads but nothing on it works."
- Why this is a bigger deal than a normal bug: **the app was effectively unusable for the actual customer this entire build**, despite 60+ backlog tasks each passing independent Test verification and a full Playwright E2E suite passing 6/6 — because every single verification pass (including the E2E suite) ran from inside the same sandboxed environment as the server, which can always reach `localhost:4000` directly. Nothing in the entire QA process ever exercised the path "a real external browser, on a possibly-different machine/network-namespace than the server, hitting the app." **Lesson for any future work in this kind of environment: functional correctness inside the sandbox does not guarantee the customer's actual browser can reach the app the same way — assume ports beyond the one serving the page itself may not be reachable, and verify by asking the customer to test, not just automated in-sandbox tooling.**
- Fix: `client/vite.config.ts`'s dev server now proxies `/api` and `/socket.io` to `http://localhost:4000` server-to-server (unaffected by browser-side port forwarding, since that hop never involves the customer's browser). `apiClient.ts`'s `API_BASE_URL` now defaults to `''` (same-origin relative paths) instead of the hardcoded port, so the browser only ever needs to reach the one port that's already proven reachable (wherever the page itself loaded from). `socket.ts` connects with no explicit URL when `API_BASE_URL` is empty (falls back to the page's own origin, which `io()` handles correctly but `io('')` does not). `VITE_API_BASE_URL` remains available and documented for a genuine future cross-origin deployment.
- Verified: full Playwright E2E suite still 6/6 passing (including the Socket.IO-dependent Listening spec, confirming the websocket proxy works with `ws: true`), typecheck/lint/build clean, curl against the proxied port (`http://localhost:5173/api/auth/register`) succeeds identically to the direct port. All temporary diagnostic logging was removed after the root cause was confirmed.
- Status after this entry: fixed and committed (`73b2fe3`). Combined with the earlier same-session fix for the dead top-nav/scaffold home page (previous entry below), these were customer-reported UX/functional issues found only by actually having the customer use the running app after the backlog was declared "complete" — both are now resolved.
